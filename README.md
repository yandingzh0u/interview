# 面试题库

本地运行的面试题背题工具。自己录题，按答题骨架分段，空格逐段揭示答案。

## 运行

Windows 双击 **`启动.bat`**，浏览器会自动打开 `http://127.0.0.1:7788`。

或者命令行：

```bash
node server.mjs
```

需要 Node.js 18+。零依赖，不用 `npm install`。关闭那个黑窗口就是停止服务，数据已经存盘。

## 怎么用

1. 题库页 → 「新建题目」，或者「批量导入」粘一段
2. 选**一级 Tag**（选大类，决定下面有哪些问法）和**二级问法**（决定每一步叫什么）
3. 按骨架分段填答案，每段一个输入框
4. 背诵页按空格逐段揭示

键盘：

| 键 | 作用 |
|---|---|
| `空格` | 展开下一段 |
| `→` | 下一题 |
| `←` | 上一题（直接全展开） |

## 五个一级 Tag 与十三套答题方法

一道题只选一个一级 Tag、一个二级 Tag。二级 Tag 表示「这道题最终要交出来什么」，它决定的答法全库共用。

| 一级 Tag | 二级 Tag 与固定答法 |
|---|---|
| 解释原理 | 概念与作用：核心概括 → 补充说明<br>原因机制：结论 → 原因 → 机制<br>分类与组成：分类依据 → 主要类别及特点<br>工作流程：总览 → 分阶段展开 |
| 对比选型 | 有什么区别：比较维度 → 核心差异 → 结论<br>怎么选：判断条件 → 匹配与代价 → 什么情况选它 |
| 设计实现 | 如何设计：要解决什么 → 核心方案 → 执行流程<br>怎么落地：环境与依赖 → 接入与灰度 → 监控与回滚 |
| 排障治理 | 故障归因：现象 → 原因分类 → 触发条件<br>怎么定位：从哪查 → 排查路径 → 证据 → 根因<br>怎么处理：止血 → 根因修复 → 验证与预防 |
| 评测优化 | 怎么评估：目标与评测范围 → 评测集 → 指标与阈值 → 评测方法 → 结果分析<br>如何优化：基线 → 瓶颈 → 改进 → 对照验证 |

设计题和实现题共用「如何设计」，只回答三件事：**第一段、由什么组成、实际怎么运行**。

第一段必答，但写什么由每道题自己定。题目没说清问题边界，就写「要解决什么、有什么限制」；题目本身是「怎么规避 / 怎么保证 / 怎么防止 X」这类、问题已经给定，这一段就写一句跳过说明（「算了，跳过吧」也行），然后从「核心方案」讲起。前端不看这段写了什么、不打标、不做判断，你怎么写就怎么显示。异常处理、性能优化、验证测试不是必答步骤——它们是面试官追问时才展开的方向，记在「追问」里，不占每道题的固定位置。

**「怎么选」也收编了「为什么选 A」这类题。** 已经有方案在用时，答案同样是「判断条件 → 匹配与代价 → 什么情况选它」，只是多了一步点明原方案的缺口。

**指标设计不单独成题。** 它属于「怎么评估」的第 3 段——评什么、用什么数据、指标怎么定义、怎么跑、结果怎么读。

**同一类题共用一套方法，只换知识内容。** 比如「工作流程」永远是「总览 → 分阶段展开」：RAG 讲离线/在线两个阶段，Redis 讲建立复制/全量同步/增量同步——阶段名是内容，不是新模板。

页面上只出现这一行：

```
1 总览 → 2 分阶段展开
```

**不要求填满。** 只填要讲的段，空着的直接跳过。方法段数变少时，旧答案不会被截断，多出来的段落会显示成「补充 N」，可以并进去或删掉。

## 怎么判断该挂哪个 Tag

**先看题目要你交出来什么，再看它用了什么动词。** 同样是「为什么」，三个落点：

| 题目 | Tag | 主语是什么 |
|---|---|---|
| 为什么 MySQL 使用 B+ 树？ | 原因机制 | 技术设计本身 |
| 为什么 MySQL 会死锁？ | 故障归因 | 运行中的系统出了状况 |
| 为什么选择 Redis？ | 怎么选 | 几个候选方案 |

对应的问法：

是什么 → 概念与作用｜为什么（讲设计）→ 原因机制｜有哪些、由什么组成 → 分类与组成｜怎么运转 → 工作流程｜A 和 B 差别 → 有什么区别｜选哪个、为什么不用它 → 怎么选｜怎么造 → 如何设计｜怎么上线 → 怎么落地｜为什么坏 → 故障归因｜怎么查 → 怎么定位｜怎么修 → 怎么处理｜怎么衡量 → 怎么评估｜怎么变好 → 如何优化

## 一道题里问了不止一件事，怎么办

分三种，别一刀切：

| 情况 | 例子 | 处理 |
|---|---|---|
| 两个问题能独立提问、独立回答 | 「什么是 RAG？完整流程是什么？」 | **拆成两张题卡**，各挂一个 Tag |
| 几个问法共同构成一个考察目标 | 「相比微调，RAG 解决了什么？各自优劣势？」 | **保留一道题**，挂 `对比选型 / 有什么区别`，分维度比较 |
| 第二问是面试官可能继续深入的 | 「那你还怎么验证它有效？」 | **放进追问** |

不要为了减少题卡把独立问题塞进追问，也不要为了多录几道把一个完整问题拆碎。


## 备注

每道题都可以单独写一条备注，用来记「没懂的地方、自己的理解、面试时想补一句的话」。它不会混进答案里。

- 背诵页底部有折叠的 `▸ 备注` 一行，点开就看，按 `N` 也能展开/收起
- 折叠状态会预览前 42 个字，换题时自动收起，不会泄底
- 题库列表里，有备注的题目会多一个「备注」小标记；搜索也会搜备注内容

## 数据

| 文件 | 作用 |
|---|---|
| `data/bank.jsonl` | 题库，一行一道题 |
| `data/frameworks.json` | 骨架配置，改这里全库生效 |
| `data/history.jsonl` | 每次增删改的流水，可回放（不进版本库） |
| `data/backups/` | 每次覆盖前的时间戳快照（不进版本库） |

备份就是复制 `bank.jsonl`。它也可以直接用记事本改，改完刷新页面就生效——服务端会比对文件修改时间自动重新载入；某一行写坏了只会跳过那一行，不会毁掉整个题库。

### 改 Tag 名字不会把老题挂空

题库里每道题只记「一级 / 二级」两个名字（`cat` / `sub`），名字一改，老题就找不到自己的答题骨架了。所以改名字时，把旧名字写进 `data/frameworks.json` 里对应一级 Tag 的 `aliases`：

```json
"aliases": { "为什么出错": "故障归因" }
```

- 服务端每次载入题库按 `aliases` 对齐一遍，老题自动落到新名字上，页面上会提示「有 N 道题还挂着旧标签名，已自动对齐」
- 写入时也校验：名字对不上任何一项就**拒绝保存**，并告诉你可以选哪些，不会再静默产生挂空的题
- 确实对不上的（没有 alias 可用），载入时不会强行改，会在页面上列出来让你重选一次

## 批量导入格式

```
Q: Agent 的上下文工程怎么设计？
CAT: 设计实现 / 如何设计
SEG: 先明确任务类型、上下文窗口和延迟预算。
SEG: 按系统指令、任务状态、历史消息、工具结果四块装配。
SEG: 每轮按当前任务重新装配模型输入。
SEG: 超长时压缩历史，保留必要状态。
SEG: 用任务完成率和上下文成本验证。
FU: 压缩会不会丢关键信息？ | 看任务成功率，不看压缩率
NOTE: 这里写自己的理解，不会算进答案，可以接着写多行。
```

- `Q` 必填，`CAT` 建议填
- `SEG` 一行一段，对应骨架的每一步，可以以后再补
- `FU` 是追问，`|` 后面是答题提示
- `NOTE` 是备注，只给自己看
- 重复的题会自动跳过

## 技术

只用 Node 内置模块，没有第三方依赖。Markdown 渲染和代码高亮用 `vendor/` 里的 marked + highlight.js，已经本地化，断网也能跑。

写入采用 `.tmp` → `rename` 的原子方式，写到一半断电不会产生半截文件。
